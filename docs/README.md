# OctoAcme Project Management Documentation

Welcome to the OctoAcme project management docs. This directory contains the processes and guides used to run projects from initiation through closeout. The goal is to give teams a consistent, repeatable way to plan work, deliver value, communicate clearly, and improve over time.

## Overview

OctoAcme uses a customer-first, iterative delivery model with clear ownership, data-informed decisions, and psychological safety. Projects begin with a lightweight validation step to confirm the problem, define success metrics, and align stakeholders. Once approved, the team plans the work into manageable increments, identifies risks and dependencies, and delivers value in small, testable releases. Execution is supported by regular communication, quality checks, and defined acceptance criteria. At the end of each milestone or release, the team captures lessons learned and converts them into improvement actions.

## Core Principles

- Customer-first: prioritize customer value and usability.
- Iterative delivery: deliver small, testable increments.
- Clear ownership: each project has a named Project Manager (PM) and Product Lead.
- Data-informed decisions: measure impact and iterate based on evidence.
- Psychological safety: encourage feedback and learning.

## Key Project Management Processes

OctoAcme's project management workflow follows a simple lifecycle:

1. Initiation: confirm the business need, define success metrics, identify stakeholders, and decide whether the effort should move forward.
2. Planning: create the backlog, estimate scope, document acceptance criteria, define the Definition of Done, and map milestones and dependencies.
3. Execution: run daily standups, conduct sprint planning, track progress, review work, and resolve blockers quickly.
4. Release: verify quality, prepare release notes, deploy safely, and communicate outcomes to stakeholders.
5. Close & Improve: hold retrospectives, track action items, and use findings to improve future delivery.

This flow is intended to reduce ambiguity, improve accountability, and make team coordination easier across product, engineering, QA, and stakeholders.

## Communication and Quality Expectations

OctoAcme emphasizes regular communication and clear ownership. Teams are expected to hold recurring standups, maintain alignment between PM and product leadership, and provide stakeholder updates as milestones are reached. Project status should use a single source of truth, and blockers should escalate through defined paths to minimize disruption.

Quality is also treated as part of delivery rather than a final gate. The process expects unit testing, integration testing where relevant, end-to-end smoke tests for critical paths, security scanning in CI, and manual QA when necessary to validate acceptance criteria. Pull requests should be small and reviewable, include issue links and acceptance criteria, and require approval before merge.

## How to Use These Docs During Onboarding

New team members should begin with the [Project Management Overview](./octoacme-project-management-overview.md) to understand the project lifecycle, roles, and communication cadence. From there, they can move into the phase-specific docs that match their current work: initiation for new ideas, planning for scope and backlog decisions, execution for delivery rhythms, release for deployment standards, and retrospective for learning and continuous improvement.

These documents are intended to support onboarding, cross-functional collaboration, and continuity even as teams or priorities change. They should be treated as living guidance that can be adapted for each project while preserving the core OctoAcme practices.
